Conceptual Entity-Relationship Diagram

The diagram below visualizes the entities and their logical mappings modeled within the `garage_db` database. Relationships are established using primary-to-foreign key links.

erDiagram USER ||--o{ SERVICE_JOB : "diagnoses / completes" CUSTOMER ||--o{ VEHICLE : "owns" CUSTOMER ||--o{ SERVICE_JOB : "requests" CUSTOMER ||--o{ INVOICE : "pays" VEHICLE ||--o{ SERVICE_JOB : "undergoes" SUPPLIER ||--o{ SPARE_PART : "supplies" SERVICE_JOB ||--|| INVOICE : "generates (1:1)"

Entity Cardinality Explanations

  • Customer to Vehicle (1:N): A customer profile can own multiple vehicles, but each vehicle record is tied to exactly one customer ID.
  • Supplier to Spare Part (1:N): A vendor supplies multiple parts, but each part in the inventory matches one supplier.
  • Service Job to Invoice (1:1): A complete service job produces exactly one invoice. Managed using a unique key constraint on `invoice(job_id)`.

Relational Integrity Restraints

  • ON DELETE CASCADE: Configured on `vehicle(customer_id)`. Deleting a customer automatically removes all their registered vehicles to prevent orphaned rows.
  • ON DELETE RESTRICT: Configured on service records, invoices, and suppliers. The database rejects deletes if active transaction sheets depend on them, preventing accidental loss of historic financial data.

Academic Normalization & Transaction Analysis

1. Normalization Review & Violations

To demonstrate database design constraints for college evaluators, the schema intentionally exhibits design trade-offs:

1NF Violation Case Study

The column parts_used in the service_job table stores serialised JSON arrays containing multiple fields (part ID, quantity, price, totals).

Reason for Violation: 1NF dictates all values in a table must be atomic. Storing composite structures in a text column violates this.

How to Normalize: Create a junction table service_job_parts(job_id, part_id, quantity, unit_price) to make values atomic.

3NF Violation Case Study

The table invoice stores grand_total, labour_total, and parts_total.

Reason for Violation: Since $grand\_total = labour\_total + parts\_total$, it is a derived attribute, which introduces a transitive dependency ($\text{invoice\_id} \rightarrow (\text{labour}, \text{parts}) \rightarrow \text{grand\_total}$).

Trade-off Justification: Denormalized deliberately to minimize query latency when pulling sales metrics or rendering client summaries.

2. Transaction Processing (ACID)

Marking a service job as Completed triggers a database transaction.

# Sequence executed inside jobs.py route
START TRANSACTION;
# 1. Row-lock part inventory count to prevent concurrent edits
SELECT quantity_in_stock FROM spare_part WHERE id = ? FOR UPDATE;
# 2. Check stock levels. If count < requested quantity, abort:
ROLLBACK;
# 3. If stock is sufficient, deduct items:
UPDATE spare_part SET quantity_in_stock = quantity_in_stock - ? WHERE id = ?;
# 4. Finalise job sheet and log details:
UPDATE service_job SET status = 'Completed', diagnosis = ? WHERE id = ?;
# 5. Automatically create invoice receipt:
INSERT INTO invoice (job_id, customer_id, grand_total, ...) VALUES (...);
COMMIT;
ACID Mappings:
  • Atomicity: Rollback returns the database to its pre-transaction state if inventory levels fail, avoiding partial updates.
  • Consistency: Checks prevent stock counts from going negative.
  • Isolation: The FOR UPDATE row-lock isolates active updates from concurrent receptionist sales.
  • Durability: Once committed, records are permanently written to the MySQL storage engine.

Trigger Details

  • trg_job_completion_audit (AFTER UPDATE): Fires automatically when job status updates to 'Completed'.
